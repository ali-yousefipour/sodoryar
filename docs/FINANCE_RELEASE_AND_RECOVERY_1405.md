# راهنمای انتشار ایمن بخش مالی صدوریار (آبان/آذر ۱۴۰۵)

> این سند جایگزین تهیه پشتیبان عملیاتی یا تأیید مسئول پایگاه داده نیست. GitHub Actions فایل‌های PHP را به هاست منتقل می‌کند؛ SQL را عمداً و به‌صورت خودکار روی دیتابیس عملیاتی اجرا نمی‌کند.

## مبنا و وابستگی‌ها
- شاخه مرجع کد: `main`، مخزن `ali-yousefipour/sodoryar`.
- ساختار اولیه: `database/install.sql` و Migrationهای 001 تا 015؛ وضعیت اعمال واقعی آنها باید با پایگاه داده تولیدی مقایسه شود.
- 016: دفتر دریافت‌ها و Backfill تنها در زمان ساخت نخست جدول. **پیش از اجرای اولیه باید قطعی شود که فاکتورهای قدیمی همگی وصول‌شده فرض می‌شدند.** اگر در فاکتورهای قدیمی بدهی واقعی وجود دارد، اجرای بخش Backfill بدون تطبیق حساب ممنوع است.
- 017: کلید یکتای دریافت بعدی برای جلوگیری از ثبت مجدد.
- 018: صندوق‌ها، شیفت، تعدیلات و شناسه شیفت پرداخت.
- 019: قفل قطعی دوره مالی؛ این قفل‌ها نباید با حذف یا ویرایش دستی دور زده شوند.
- 020: تاریخچه تغییر تعرفه؛ baseline برای خدمات موجود.
- 021: تنظیمات شخصی ایزوله کاربران.
- 022: دفتر تغییرناپذیر ثبت رسیدگی به مغایرت‌ها.

## مراحل اجرایی مجاز از طریق phpMyAdmin
1. از پایگاه داده واقعی **ساختار و داده‌ها** خروجی SQL کامل، با شناسه، زمان و نسخه MariaDB تهیه و در محل امن خارج از وب‌روت نگهداری کنید. از صحت حجم، بازشدن فایل و امکان بازیابی آن در پایگاه داده مجزای آزمایشی مطمئن شوید. داده‌های واقعی را وارد مخزن نکنید.
2. محیط آزمایشی را با نسخه‌ای سازگار از دیتابیس و PHP آماده کنید و Migrationهای موردنیاز را **به ترتیب عددی** وارد کنید. خروجی هر اجرا و خطا را بررسی و تست عملیاتی انجام دهید.
3. در پنجره نگهداری، پس از گرفتن پشتیبان مجدد و اطمینان از عدم ثبت فاکتور هم‌زمان، `database/migrations/016_invoice_payments.sql` را بررسی و فقط در صورت نیاز اجرا کنید. ممکن است قبلاً نصب شده باشد.
4. با توجه به وضعیت واقعی جدول، Migrationهای `017_invoice_payment_idempotency.sql` تا `022_financial_issue_reviews.sql` را **به ترتیب** اجرا کنید؛ هر فایل در یک بار Import مستقل. مرحله بعدی فقط پس از تطبیق خطا و اعتبارسنجی قبلی مجاز است.
5. Migrationهای 017، 018، 019، 020، 021 و 022 برای اجرای دوباره طراحی شده‌اند؛ با این وجود قبل از تکرار در محیط عملیاتی تغییرات دستی schema و وضعیت Foreign Keyها را کنترل کنید.
6. از طریق UI مدیر شرکت، ابتدا دستگاه‌ها و صندوق‌های واقعی را تعریف کنید، سپس پرداخت ترکیبی/مانده، تسویه صندوق، گزارش‌های مالی و قفل دوره را در نمونه‌های غیرواقعی تست کنید. **هیچ تراکنش صوری بانکی را موفق واقعی ثبت نکنید.**
7. هرگز به‌دلیل شکست Migration از حذف جدول مالی یا حذف سابقه استفاده نکنید. DDL ممکن است به‌صورت implicit commit اجرا شود. بازگشت صرفاً طبق برنامه تهیه‌شده و با بازیابی پشتیبان سازگار مجاز است.

## کنترل‌های SQL صرفاً خواندنی
```sql
SHOW TABLES LIKE 'invoice_payments';
SHOW TABLES LIKE 'cash_shifts';
SHOW TABLES LIKE 'financial_period_locks';
SHOW TABLES LIKE 'service_rate_versions';
SHOW TABLES LIKE 'user_preferences';
SHOW TABLES LIKE 'financial_issue_reviews';
SHOW COLUMNS FROM invoice_payments LIKE 'request_key';
SHOW COLUMNS FROM invoice_payments LIKE 'cash_shift_id';
SELECT COUNT(*) AS invoice_count, COALESCE(SUM(total_amount),0) AS invoice_amount FROM invoices;
SELECT COUNT(*) AS payment_count, COALESCE(SUM(amount),0) AS recorded_payment_amount
FROM invoice_payments WHERE voided_at IS NULL;
SELECT company_id, COUNT(*) AS count_rows FROM invoices GROUP BY company_id;
SELECT company_id, COUNT(*) AS count_rows FROM invoice_payments GROUP BY company_id;
```

**نکته حسابداری:** مجموع صدور فاکتور و مجموع دریافت‌های واقعی دارای تاریخ و مفهوم متفاوت‌اند؛ اختلاف ساده آنها بدون درنظرگرفتن ابطال و تاریخ مبنا معیار قطعی مانده یا موجودی صندوق نیست.

## شواهد CI
- `.github/workflows/php-check.yml`: lint PHP، فایل‌های JavaScript و تست‌های امنیتی/بومی‌سازی.
- `.github/workflows/deploy-shared-host.yml`: تست MariaDB ایزوله، مرورگر، چاپ، بازیابی dump در دیتابیس آزمایشی، سپس آپلود FTP و تأیید Manifest.
- `integration/mysql-tenant-smoke.php`: Migrationها و داده‌های دو شرکت کاملاً ساختگی؛ استفاده از آن روی دیتابیس تولیدی به‌صورت صریح مسدود است.
- `scripts/verify-disposable-restore.sh`: تنها روی پایگاه داده `sodoryar_integration_test` در `127.0.0.1` اجرا می‌شود و هیچ دیتابیس تولیدی را لمس نمی‌کند.

## مواردی که نمی‌توان تنها از مخزن تأیید کرد
وجود پشتیبان معتبر دیتابیس واقعی، تطبیق تراکنش واقعی بانکی، وضعیت اجرای Migrationهای تولیدی، حقوق کاربران و کیفیت اتصال کارتخوان، چاپگرهای واقعی و Restore از داده‌های تولیدی. این موارد باید با دسترسی و شواهد محیط عملیاتی تأیید شوند.
