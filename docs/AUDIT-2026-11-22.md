# گزارش ممیزی و توسعه صدوریار — ۱۴۰۵/۰۹/۰۱ (۲۲ نوامبر ۲۰۲۶)

**مخزن مستقل:** `ali-yousefipour/sodoryar` — **شاخه:** `main`.

## وضعیت واقعی
اصلاحات در کد ثبت شده‌اند؛ به دلیل شکست GitHub Actions پیش از اجرای Stepها، **موفقیت آزمون‌های CI، انتشار روی هاست و اعمال Migrationها تأیید نشده است**. این سند به منزله تحویل نهایی عملیاتی نیست.

## اولویت ۱ — CI و انتشار
- Deployment قبل از انتقال فایل‌ها، Lint PHP و JavaScript و آزمون‌های `tests/*.php` را اجرا می‌کند.
- فایل‌های `_private/` قبل از `public/` انتقال داده می‌شوند.
- پس از آپلود، `sodoryar-version.json` با `GITHUB_SHA` و Hash فایل‌های JS/CSS مقایسه می‌شود.
- FTPS تنها با گواهی معتبر ادامه می‌یابد: `ssl:verify-certificate yes`. گواهی فعلی میزبان باید توسط مالک هاست اصلاح شود.
- **مانع خارجی:** Jobها با `steps=[]` و بدون Runner قابل شناسایی شکست می‌خورند. Issue: https://github.com/ali-yousefipour/sodoryar/issues/16

## اولویت ۲ — امنیت چندشرکتی
- شرکت انتخاب‌شده مدیر کل در هر درخواست از نظر فعال‌بودن اعتبارسنجی می‌شود.
- بررسی نقش و مجوز نامعتبر به صورت Fail Closed است.
- محدودیت مشاهده سند مالی برای اپراتور: `own` یا `company`؛ با Migration اختیاری `011`.
- محدودیت مالکیت برای مشاهده، چاپ، ویرایش پرداخت و ابطال فاکتور؛ گزارش‌های مالی، داشبورد، فیش‌ها، فعالیت‌ها و پورسانت.
- تمام درخواست‌های حساس با مجوز سمت سرور و Tenant Context پردازش می‌شوند.
- آزمون‌های افزوده‌شده در `tests/tenant-security-contracts.php` و `tests/security-document-scopes.php` **آزمون ایستای قرارداد هستند، نه آزمون یکپارچه با DB واقعی**.

## اولویت ۳ — نقش‌ها و مجوزها

- Migration `010_company_roles.sql` باید پس از پشتیبان‌گیری اجرا شود.

## اولویت ۴ — صحت عملیات مالی و فیش‌ها

## راه‌اندازی ایمن
1. ابتدا مشکل Runner/Actions و گواهی معتبر FTPS رفع شود. انتشار ناامن را با غیرفعال‌کردن اعتبارسنجی گواهی دور نزنید.
2. از پایگاه داده و فایل‌های آپلودی **نسخه پشتیبان قابل بازیابی** تهیه و بازیابی آن را آزمایش کنید.
3. Migrationهای `009`، `010` و `011` را روی محیط آزمایشی و سپس روی هاست با نظارت اجرا کنید. کد جدید در نبود Migrationها تلاش می‌کند ماژول‌های وابسته را غیرفعال نگه دارد.
4. آزمون واقعی دو شرکت A/B و کاربر فقط-اسناد-خود اجرا شود؛ تلاش تغییر ID و درخواست مستقیم API باید 403 یا نتیجه خالی بدهد.
5. آزمون صدور هم‌زمان، ابطال، تغییر مجوز، حذف فیش و بازیابی و کنترل مانده مالی اجرا شود.
6. چاپ A5 و رول ۸۰ میلی‌متری در مرورگر و دستگاه واقعی بررسی شود.
7. فقط پس از CI سبز، بررسی نسخه روی هاست و تأیید Migration، نسخه را «عملیاتی» اعلام کنید.

## تکمیل ممیزی جاری — شواهد جدید

### امنیت هویت و کنترل دسترسی
- جلوگیری از انتساب مستقیم/نقش ارثی مجوزهای مدیریتی به اپراتورها؛ دسترسی کاربر صرفاً دارای `invoices.create` به صفحه صدور بدون افشای سوابق.
- دسترسی داده‌های مالی در صورت خطای خواندن جدول ابطال، Fail Closed است.
- `database/migrations/014_session_revocation.sql`: نسخه نشست کاربر؛ در صورت نصب Migration، تغییر رمز، تغییر نقش، تغییر وضعیت و بازنشانی رمز از پنل مدیریت، نشست‌های قدیمی در درخواست بعدی رد می‌شوند. نصب Migration باعث خروج مجدد نشست‌های قبلی فاقد نسخه خواهد شد.

### رابط کاربری و قالب‌ها
- پشتیبانی از A4 علاوه بر A5 و رول ۸۰ میلی‌متری، با Migration شماره `012`.
- قابلیت ویرایش قالب‌های چاپ ذخیره‌شده (عنوان، کاغذ، فونت، عرض رول، سربرگ و پانوشت)، ضمن حفظ لوگو و ترتیب بخش‌ها.
- دریافت Excel با `report-progress.js` از طریق Streaming و نمایش درصد **فقط هنگام وجود Content-Length معتبر**؛ خطا/پاسخ HTML و دریافت ناقص فایل تشخیص داده می‌شود.
- آزمون رفتاری این JavaScript با داده مصنوعی در موتور V8 انجام شد: پاسخ XLSX سالم باعث یک دانلود شد؛ پاسخ HTML باعث صفر دانلود و پیام خطا شد. این آزمون جای آزمون Browser E2E نیست.

### ساختار دیتابیس
- `013_tenant_query_indexes.sql` ایندکس‌های فیلترهای مالی/شرکتی را افزایشی و با کنترل وجود قبلی اضافه می‌کند.
- `schema.sql` و `install.sql` نیز برای نصب تازه با نقش‌ها، فیش‌های قابل بازیابی، نسخه نشست، محدوده اسناد و فرمت چاپ جدید همگام شدند.
- برای بانک موجود، همچنان Migrationهای `009`، `010`، `011`، `012`، `013` و `014` **پس از Backup و آزمون Staging** لازم هستند.

### وضعیت انتشار و اثبات کیفیت
- Source checks و بررسی ساختاری چند قرارداد کد در GitHub و موتور V8 موفق بودند، اما CI برای جدیدترین کامیت‌ها همچنان قبل از اختصاص Runner شکست می‌خورد.
- تست‌های PHP در GitHub Actions **اجرا نشده‌اند**، Migrationها روی هاست **اعمال نشده‌اند**، و صحت چاپ/فرم‌ها روی دامنه عملیاتی **تأیید نشده است**.

## ممیزی تکمیلی امنیت و معماری — آخرین اجرا (۲۲ نوامبر ۲۰۲۶)

### نقص‌های مشخص و اصلاح‌شده در همین اجرا
1. **خرابی Parser گزارش‌ها:** دو رشته SQL در `src/reporting.php` به دلیل Escape‌نشدن `'superadmin'`، موجب PHP ParseError می‌شدند. رشته‌ها اصلاح شدند و تست بدون اجرای دیتابیس `tests/php-source-parse.php` به CI اضافه شد. معادل حداقلی دو رشته در PHP 8.4 با `php -l` موفق بود. **Lint کل مخزن در GitHub هنوز اجرا نشده است.**
2. **افشای تاریخچه فاکتورها در داشبورد:** داشتن `reports.view` برای دیدن فاکتورهای دارای اطلاعات تاکسیران کافی بود؛ اکنون `invoices.view` برای نمایش تاریخچه و تابع `render_invoices` ضروری است. دیالوگ ویرایش پرداخت نیز به `invoices.payment_edit` محدود شد.
3. **Race Condition در مدیر آخر شرکت:** تغییر نقش، غیرفعال‌سازی و بایگانی از این پس در تراکنش و با قفل فهرست مدیران فعال (`FOR UPDATE`) انجام می‌شود تا دو درخواست هم‌زمان آخرین مدیران را حذف نکنند.
4. **عدم لغو نشست مدیر شرکت:** تغییر رمز یا نام کاربری مدیر توسط مدیر کل، در صورت نصب Migration شماره `014`، `auth_version` را افزایش می‌دهد.
5. **مغایرت Schema نصب تازه:** ستون `auth_version` اشتباهاً به `companies` اضافه شده بود، نه `users`. هر دو فایل `database/schema.sql` و `database/install.sql` اصلاح شدند.
6. **ناسازگاری CSP:** عرض میله‌های داشبورد با `style` درون‌خطی تعریف می‌شد که با CSP فعلی ناسازگار است؛ با `progress` بومی و CSS خارجی جایگزین شد. پیش‌نمایش لوگوی چاپ که از `blob:` استفاده می‌کند، اکنون در `img-src` مجاز است.
7. **کد ملی با ارقام فارسی:** ورود کد ملی دارای ارقام فارسی یا عربی در ثبت راننده و صدور فاکتور به ارقام انگلیسی استاندارد تبدیل می‌شود.
8. **پیش‌فرض چاپ:** در نبود قالب ذخیره‌شده، سند A4 نمایش داده می‌شود؛ قالب‌های قدیمی A5 و حرارتی ۸۰ میلی‌متری محفوظ‌اند.

### پوشش آزمون
- اسکریپت‌های جدید: `php-source-parse`، `invoice-history-authorization`، `admin-roster-serialization`، `admin-manager-session-revocation`، `dashboard-csp-progress`، `csp-company-logo`، `driver-national-input-digits`، `session-version-schema`.
- هر سه JavaScript پروژه با Parser موتور V8 بدون خطا بررسی شدند.
- بخش مرتبط با اصلاح SQL گزارش‌ها به‌صورت نمونه مستقل با PHP 8.4 بررسی شد.
- محل قرارگیری `auth_version` در هر دو Schema به‌صورت ساختاری تأیید شد (فقط `users`).
- **تست‌های PHP سراسری، تست یکپارچه واقعی MySQL و تست E2E اجرا نشده‌اند؛** GitHub Actions همچنان پیش از شروع Stepها شکست می‌خورد.

### محدودیت انتشار
در اجرای اخیر نیز GitHub Actions با `runner_id=0` و `steps=[]` شکست خورد. تا زمان رفع محدودیت Runner و تأیید گواهی FTPS، Migrationها و انتشار عملیاتی نباید موفق گزارش شوند. تغییرات به‌صورت کد روی `main` ثبت شده‌اند، نه به‌صورت نسخه تأییدشده روی هاست.

### موارد باز برای تکمیل ۱۱ مرحله
- CI و FTP، محیط Staging واقعی و اجرای Migrationهای `009` تا `014`.
- تست امنیت با دو شرکت و اکانت‌های واقعی آزمایشی، QA حسابداری و هم‌زمانی با MySQL.
- بررسی واحد پول ریال/تومان در تمام فیلدهای ورود و خروج: **تکمیل نشده و نیازمند سیاست مهاجرت بدون تغییر مبلغ‌های ذخیره‌شده است**.
- آزمون UI/UX در مرورگرها و موبایل، چاپ A4 و حرارتی واقعی، Load Test و Backup/Restore.
- بررسی صحت نسخه منتشرشده و اجرای Smoke Test در دامنه عملیاتی.

**وضعیت نهایی: اجرای کدنویسی و ممیزی ایستا ادامه یافته، ولی مجوز تأیید انتشار Production وجود ندارد.**
